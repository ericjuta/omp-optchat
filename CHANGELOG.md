# Changelog

## Unreleased

- **Changed: a second session outside git no longer runs without memory.** Without `--optchat-dir`, every session outside a git checkout used the one global `optchat/` store, so starting OMP in a second such directory warned "OptChat is inactive: … is in use by another session". When the global store is held, the session now opens its working directory's own store under `optchat-dirs/<name>-<sha16>` beside it and reports the directory in one notice; it goes inactive only if that store is held too. An explicit `--optchat-dir` never falls back.

- **Fixed: a close error after a successful `/optchat new` rename no longer reports the archive as failed.** `Store.archive` threw "Failed to close Store resources" when a stream, the root descriptor or the lease failed to close after the directory had already been renamed, so `/optchat new` said it could not archive the chat and did not reopen, though the chat was moved. Once the rename has succeeded, `archive` now returns the archive path and reports the close errors as a warning naming it; a failure before or at the rename still rejects with nothing moved. The lease is still released exactly once.

## 0.13.1 — 2026-10-21

Two findings of `bun run verify:lease` (the TLA+ model and real-process checks of the store's writer lease), both fixed. Each fix has regression tests that fail on 0.13.0.

- **Fixed: `/optchat new` could archive a store that another session had open.** It closed the store, which released the lease, and then renamed the directory by pathname holding nothing. A session that opened the directory in that gap lost its live store to the archive, and kept writing into the directory the user was told was closed. The store now archives itself (`Store.archive`): it keeps its lease and root descriptor through the rename and releases them after. It renames only while the path still names the leased inode; if the path was moved or replaced, `/optchat new` fails with "Refusing to archive …", renames nothing, and reopens as it does for any archive failure. A concurrent user `mv` between that check and the rename stays possible, since rename takes a pathname.
- **Fixed: the rules ledger and `metrics.jsonl` were written by pathname, not into the store the session holds.** The store follows its inode after the directory is moved, but `ledger.jsonl` and `metrics.jsonl` were opened as `<directory>/…` on every write, so after a move (a user `mv`, or the archive race above) rules and metric rows landed in whichever store was now at that path. Both are now resolved through the held root descriptor (`Store.sidecarPath(name)`, valid only synchronously and only while the store is open). A metric row for a store that is closed or whose lease failed is dropped without a warning per row; the store already reported its failure. `OPTCHAT_METRICS_FILE` still wins.
- **Changed (internal API): `archiveStoreDirectory` is removed** in favor of `Store.archive(now, report?)`, and `RuleLedger.open` takes a resolver `() => string` (called at open and at each write) instead of a directory. `nextArchivePath` stays.

## 0.13.0 — 2026-10-21

From a read-only audit of 15 real sessions, 10 stores and 9,920 compressor metric rows, and Jev verdicts on 121 memory-tool calls (found 77, partial 29, miss 11, error 3, unclear 1). Every fix has a test that fails on 0.12.0.

- **Fixed: `work(name)` finds subagent reports.** Four of the five audited `work` calls failed with `no captured work is recorded`: a `task` spawn stores a pointer-only record, and the finished reports arrived inside `wait` results that were logged as plain tool output. Each completed task job in a `wait` result is now its own work record with its job id and agent name.
- **Fixed: tool output is no longer summarized as the user's words.** A compressor line whose messages hold no user message may not carry a `user:` tag; it is retried like a head, and if every try repeats it the tag is cut (`userRetries` in `/optchat status`). Since 0.10.3, 6 leaves and 44 merges had carried a false `user:` tag.
- **Changed: leaf lines open with their source kind, written by code.** The compressor had invented `finding:`/`decision:` labels on up to 26% of a store's lines, and the style spread through merges. A leaf line now opens with `user:`, `talk:`, `tool:`, `echo:`, `work:` or `note:`, which replaces any other leading label and counts toward the byte limit. Merges and verbatim nodes are unchanged.
- **Changed: a tool call's `zoom` page names its result** (`[result: message N]`). Five of the 11 audited misses zoomed the call instead of the result. Pairing is by position, since the store keeps no tool-call id.
- **Changed: `chat_search`.** `before` must be at least 1 (0 could never match; the G5 golden is re-pinned for this one schema line). A multi-word search with no hit lists how many messages hold each word and, when `chat_recall` is registered, suggests it.
- **Changed: compressor cache anchor.** OptChat's trailing system block gets its own cache marker behind the host's stable anchor (four markers at most), so a change early in the view no longer rewrites the system prompt. In the audit, 361 cold rebuilds (3.6% of calls) were 40% of $311 spend. No saving is claimed until a week of metrics before and after compares the cold-rebuild share.
- **Changed: `metrics.jsonl` rows.** Compressor rows carry `type`, `at`, `node` (leaf or merge), the true `attempt`, the `retry` cause and `waitMs` apart from provider `latencyMs`; `purpose` is gone. Host compactions (`marker`, `cut-moved`, `cancelled` with a reason) and rules triage (P(rule), cutoff, added; no text) get rows of their own. Spend counts compressor rows only; untyped older rows still count as compressor calls.
- **Changed: an inactive session says why in its session log** (`optchat-inactive` entry with the reason and store directory), not only in a UI notice.
- **Docs:** README recommends `compaction.thresholdTokens` of about 200,000–300,000, since marker compactions are free and OMP's own side requests send the raw history (12 "prompt is too long" failures before 0.12.0).
- **Not adopted (pre-registered, plan Decision Log 2026-10-21):** a compressor system prompt of OptChat's guide alone, instead of the host's prompt plus the guide. On 40 real compaction tasks (seed 20261021, blind pairwise assessors) it was better on 26, worse on 11 (3 ties) and cost $0.0155 vs $0.0480 prompt per call, but its first replies broke a hard rule 12 times vs 9 (all over the byte limit; after retries both arms stored 1 violation each). The frozen rule counts first replies, so the host prefix stays. Run cost $4.04 of $5; scripts in `evals/compressor/`.
- **Not changed:** stand-ins from compressor refusals are not re-summarized when a store opens, because a store refuses a second, different row for the same tree node and older plugin versions could not open a store that had one.
- **Measured, not changed:** with a loopback model, a turn's first request differs from the previous turn's last only at the old view's tail (92% of bytes shared) except when the view coarsens, which rewrites the view; this does not explain the live 38–55% turn-start cache reads. A 330k-token tool-heavy turn is 88% open-turn messages, 10% host system prompt and under 1% OptChat.

## 0.12.0 — 2026-10-20

- **Fixed: OMP no longer shows "Auto context-full maintenance cancelled" over and over in a long chat.** OMP decides when to compact from its own estimate of the raw history it holds, not from what the model was sent, and OptChat cancelled every compaction. Once that raw history passed the threshold, every check (before each prompt, after each run, and between tool calls) started maintenance and was cancelled. OptChat now answers a host compaction (automatic, `/compact`, or the experimental rollover) with one fixed marker summary and makes no model call. OMP drops raw history the model never reads, since the view already carries it, and its checks stay quiet until the raw history passes the threshold again. A compaction never cuts the open turn: the cut moves to the turn's first message, or OptChat cancels it when nothing older can go. A host compaction summary in the message list is never logged or sent after the view. `/optchat status` describes this.
- **Evidence:** a live check on the installed omp 18.12.3 with a loopback model (threshold 30,000 tokens, experimental rollover on as in Eric's config, 20 prompts of about 18 KB) showed 28 cancelled maintenance runs and no compaction on 0.11.1. This release ran 3 marker compactions and no cancelled run, with the same 20 main and 61 compressor requests, and the marker never reached the model. The classic path, run for 8 prompts, showed the same pattern: 4 cancelled runs before, 1 marker compaction after. Three real-host cases (rollover, classic, and a tool loop that crosses the threshold mid-turn) fail on 0.11.1 and pass now; unit tests are in `tests/compaction.test.ts`.
- **What changes for you:** after a host compaction, OMP shows the marker in place of the older transcript, as it does for any compaction. The full history stays in OptChat's log and tree (`zoom`, `chat_search`, `chat_recall`) and in the session file. A long session compacts once at its first check after upgrading. The evidence runner counts a marker compaction at exactly zero cost, since it makes no model call.

## 0.10.3 — 2026-10-17

- **Fixed: concurrent cold compressor calls no longer each write the whole system prefix.** The cache coordinator keyed only on message marks, and each compressor call's last mark is its own task line, so no two calls ever waited for each other: in a cold 64-message build, 7 concurrent leaf calls each wrote about 66K tokens and read none ($0.167–0.173 each). A compressor call now also keys on its anchored tools and system head, so later calls wait for the first writer's response to start and then read the prefix. Main requests never wait on a head alone, the 20 s fail-open stays, and no prompt or tool bytes change. Live check after the change, n = 3 with no same-session control: the first call wrote 65,171 tokens ($0.1646), the next two read 61,980 each ($0.0163, $0.0158). Tests in `tests/cache.test.ts`.
- **Fixed: no stored line is the bare `[unsummarized: compressor refused]` marker.** Eight lines in one live store were exactly the marker, all written by the compressor copying it (the code's own stand-in always carries an excerpt). A reply that opens with the marker, after any heads, is now retried like a head, and when no other reply is usable the compaction falls back to the marked source excerpt. A summary that mentions the marker later in the line is kept. Earlier lines are unchanged. Tests in `tests/memory.test.ts`.
- **Not changed:** the compressor keeps the host system prompt as its shared prefix (prompt bytes and the G5 golden unchanged). No rules round on precision: the three non-rule messages the gate added on the fresh set are borderline standing instructions, and 6 labeled rules in 120 messages cannot ground a ratchet; rule-add stays 0.8.

## 0.10.2 — 2026-10-17

It now stores that reply with its detected heads cut; a reply that is nothing but heads is kept whole. `Merged a+n and b+n.` naming the line's own range and `Compaction output:` are now detected as heads. - **Evals, no behaviour change:**

The 0.10.0 gain therefore holds for agent replies too, not only tool results.

## 0.10.0 — 2026-10-16

- **Changed default: `chat_recall` scans the messages under its top lines.** The halving descent is gone. Seeds: the word search's widest pool is re-ranked locally with BM25-style length normalization (no model call), so a short message that states the answer outranks a long dump; the top `--optchat-recall-seeds` become single-message candidates. Scan: view lines and seeds are scored in the same relevance requests as before; if no line reaches `--optchat-recall-min` the outcome is `none`; otherwise the top `max(k, 4)` multi-message lines at or above `--optchat-recall-min` are scanned, and every built message under them is scored in one more round of the same requests, at most 256 messages (a line whose unscored messages would pass the cap is skipped whole, and listed as a failed other when k > 1). Pick: the single-message candidates that reached `--optchat-recall-min` or lie under a scanned line, plus the scanned messages, are ranked by score; those within 0.1 of the best (at most 8) are shown side by side in one choice question, in message order, and the likeliest wins; a failed pick keeps the score ranking, and no question is asked unless 2 or more messages contend. The result path is the scanned line covering the message, then the message, with its first 8,000 bytes. The descent prompt (`RECALL_DESCENT`) is removed. `--optchat-recall-k` (default 1, 1–8) now widens the scan beyond 4 lines and, above 1, lists the losing messages as others. Judge calls per recall: about ⌈(lines+seeds)/64⌉ scoring requests, plus 1–4 scan requests, plus at most 1 pick; bounds are unchanged (20 s overall, 5 s per judge call), and recall never throws.
  - **Why:** in the failing train attempts of the recall ratchet, the answer sat under the 2nd–4th line or a near-tied candidate, which a one-way descent from the top line could not reach.
  - **Evidence:** the `chat-recall-sets` ratchet gate reverted the change as round v4 (train 0.769 vs 0.620, held-out 0.736 vs 0.694 ±0.143, inside noise), so it was adopted on a pre-registered confirmation: 60 fresh real questions, written blind and graded by blind assessors, 3 runs per arm (seeds 8, k 1). The baseline answered 61 of 180 runs, the scan 116 of 180; the scan was better on 23 cases and worse on 2. The golds were 55 tool results and 5 agent replies, because the packet order put the rarer reply candidates last, so the gain was measured mostly on tool-result answers: on the fresh questions answered by a tool result the scan was better on 20 cases and worse on 2 (108 vs 58 passing runs of 165), on the 5 fresh questions answered by an agent reply 3 better and 0 worse, and on the 12 held-out flow cases answered by an agent reply the two searches tied (16 vs 16 passing runs, 1 better and 1 worse). Pooled with the 36 held-out flow cases (5 better, 3 worse), a one-sided sign test over 96 cases gave 28 vs 5, p ≈ 3e-5. Cost is the same (1,189 vs 1,203 judge calls per 180 recalls, $0.33 per 180); latency p50 0.80 s vs 0.62 s, p90 1.11 s vs 1.62 s; `none` outcomes fell from 23 to 7 of 180. Judge: typesafe/jev-1.14 through the `judge` role.
- **Changed: system prompt.** The `chat_recall` line describes the scan instead of a per-level descent. The prompt is sent with every gate off too, so the gates-off golden is re-pinned to 0.10.0 (a 4-line golden diff) and the system block is 6330 bytes (was 6316).

## 0.9.4 — 2026-10-15

- **macOS support for `Store`:** on `darwin`, `Store.open` acquires an exclusive non-blocking `flock` lease on the held root directory descriptor and resolves open file and directory descriptor paths through `fcntl(F_GETPATH)` (`fdPath`). Like the Linux abstract Unix socket and `/proc/self/fd` implementation, it creates no lock file in the store directory, releases ownership on `close` or `SIGKILL`, and keeps stream and snapshot writes anchored to the leased vnode across renames.
- **`evals/recall/` accepts more than one right answer for a real case:** a `real-spec.json` entry may list `also`, other messages of the same store that answer the question as well as the gold, and the grader passes either. It also lists `no` (messages judged not to answer) and a required answer `key`: an answer nobody judged passes iff the page recall returned contains every phrase of one key alternative. The builder checks that each key matches the gold and every `also` page but no `no` page, and result rows record `judged`. The sets came from blind pooling: candidates were the gold's neighbours, the question's word-search matches and every message a recorded run answered, and assessors judged them from the chat text alone, without seeing which message any run picked. Coverage mode also reports where the gold ranks in raw-log word search. The real set grew from 18 to 60 cases, with questions written blind from the chat text. Real cases stay in gitignored files.

## 0.9.3 — 2026-10-14

- **Compressor replies that open with their own message id are retried.** After 0.9.2 the head guard caught none of the live heads it knows (63.9% → 0%), but colon-less openings that name the task's own ids ("1197 Live …", "Message 1185 records …", "1191 ← store check") still reached 9.9% of new lines here and 29.1% in another store. `compact()` now also treats a leading number inside the task's own message range, with an optional "Message"/"Echo"/"Line" word and arrow or dash, as a head. A number outside that range ("7 rows found") is not. On this repository's live tree the check flags 195 of 2,576 stored lines.

## 0.9.2 — 2026-10-14

- **`evals/rules/` (`bun run evals:rules`):** an eval for the rules-triage gate. It runs the production triage (`triageState`, `triageQuestions`, `decideTriage` at `--optchat-rule-add`) over synthetic and real user messages, and scores each decision against its label: precision, recall and F1 over rule adds, and a per-case pass rate (`score`). Triage wording moved to `src/system1/rules-prompt.ts` (requests are byte-identical, pinned by `tests/rules-prompt.test.ts`). Real messages stay in gitignored files.
- **`evals/gates/`:** fixed hand-written sets for rubric hard gates G1 (injection obedience, 20 cases) and G3 (status inflation, 20 cases), run through the real compressor step with deterministic checks; flagged lines go to a human-review list, never auto-confirmed.
- **Compressor replies that open with a head are retried.** 36% of this repository's live summary lines (709 of 1,946) began with an `id+n|` head, a label ("Compacted line (≤512 bytes):", "Merged line (476+2):"), a tag (`<merged-line id=…>`, `<summary>`) or commentary, which the system block forbids. `compact()` now detects such a head and spends one of its `tries` on a feedback turn asking for the line alone; the echoed reply has the head cut, so no ids go back into compressor input. The first clean fitting reply wins; if every try is headed, the first fitting headed reply is kept as before (nothing is truncated or rewritten). Ordinary openings such as `user: …` or `Finding: …` are not heads.
- **`evals/gates/` confirms keyword flags with Jev:** each keyword flag gets one `judge`-role judgment; P(yes) ≥ 0.5 goes to the human-review list, below it the flag is recorded as auto-dismissed. Judge errors and the cost ceiling go to review, never dismissal. Rerun: G1 and G3 had no lines left for review.
- **`evals/rules/` reads OMP session logs:** a `real-spec.json` entry whose `store` starts with `sessions/` names a user message line in a session log, checked by SHA-256 like store messages. With 24 standing rules mined from session logs (26 real rules, 127 real cases), the gate's recall on real rules is 10/52 trials against 70/74 on synthetic ones, with no false adds: it misses terse one-line standing rules. Overall F1 0.788 (was 0.967 with 2 real rules).
- **Docs:** the design doc's status and gates-off wording now refer to the 0.9.0 memory-only golden, not v0.5.0.

## 0.9.0 — 2026-10-13

- **Changed default: `chat_recall` now seeds candidates from the raw log.** `--optchat-recall-seeds` defaults to 8, so every `chat_recall` call also scores up to 8 stored messages whose words match the question, next to the view lines. On the recall eval it answered 65/96 against 21/96 without seeds, replicated on a second run (real-only cases 11 vs 5, same direction, not significant). Cost: at most ⌈(lines+seeds)/64⌉ scoring requests per call, usually the same count as before. Pass `--optchat-recall-seeds 0` for the 0.8.0 recall requests.
- **Changed: system prompt.** The `chat_recall` line describes seeding. The prompt is sent with every gate off too, so the gates-off golden now pins 0.9.0 bytes (a 4-line prompt change) and the system block is 6316 bytes (was 6277).
- **`/optchat new` starts a fresh chat without losing the old one:** the current store moves byte for byte to a sibling archive `<dir>.<UTC stamp>` (a numeric suffix if taken), and an empty store opens at the original path through the normal start path (flags, gates, an empty rules ledger, child-view publishing). It needs this session's memory open and the agent idle, and asks for confirmation when a UI exists, naming the archive. A failed archive reopens the original store; a failed fresh open reports the archive path and `--optchat-dir <archive>`. OMP's `/new` still keeps the same OptChat memory.
- **Docs:** README corrects the gate count and the judge cost (one rules request per user message; on a merged-view turn one prefetch request per chunk of up to 64 view lines, 3 per such turn in the live run). Status judge-call counters include shared-cache answers, so billed usage can be lower.
- **Recall adds raw-log matches as candidates (`--optchat-recall-seeds`, default 8, integer 0–32; `0` restores the previous requests and output byte for byte):** `Memory.rankMessages(question, { limit, before })` ranks stored messages by the question's words, weighted by inverse document frequency, with no model call and the same skip rules and `before` bound as `search`. Each of the top seeds becomes a single-message candidate (its first 4 KB), scored in the same relevance requests as the view lines and ranked with them; a raw-log winner is labelled as such. Why: summaries kept the fact for only 11 of 48 gold messages that a view line covered, so descent from summaries could not reach most answers. Recall eval, k=1, 48 cases × 2 reps per arm, cap 1500 judge calls per arm: seeds 8 answered 65/96 against 21/96 for seeds 0, and a replicate run gave the same counts (synthetic 54/60 vs 16/60, real 11/36 vs 5/36, paraphrase 4/10 vs 0/10). Raw-log winners were right 62 of 72 times, view-line winners 3 of 24. Run totals were 290 judge calls for seeds 8 against 383–387 for seeds 0 (budget cap 1500 per arm). No trial in the four runs hit an internal judge error. The real-only gain is weaker (paired sign test p≈0.11 per run); the synthetic gain is strong. Scan cost of `rankMessages`: median 0.2 ms on the synthetic 256-message trees, about 6 ms per question on the 1,637-message store (`optchat-main`).
- **Standing instructions have three scopes:** the rules ledger holds instructions you state in this chat, per store; OMP TTSR rule files hold enforced guardrails for every session; Sharpshooter holds cross-session project decisions learned from friction. README (the rules bullet under the gates) and `docs/design/optchat-jev.md` §3.3 say so.
- **`evals/recall/` scoring:** a found or none outcome is scored as recall returned it, even when a judge call inside it failed; rows record `internal_judge_errors` and `raw`. Only attempts with no outcome are retried, and after retries they go to `errors.jsonl`, never to a zero in `results.jsonl`. The earlier strict rule that scored a pass after a retry as a fail is gone. `--seeds N` sets seeds (default: the shipped default), recorded in `run.json`.
- **Recall descends from the top k lines (`--optchat-recall-k`, default 1, integer 1–8):** opt-in; on the recall eval k=3 scored 15/96 vs 14/96 for k=1 (within noise) for 37% more judge calls, so the default stays 1. The top k view lines at or above `--optchat-recall-min` each descend (at most 4 descents in flight, one 20 s bound), and the message with the highest path probability answers: its line's score times each choice's probability. Other candidates are listed one line each; a failed descent is listed and fails only the candidate, unless every descent failed. `--optchat-recall-k 1` is the previous single argmax descent. Judge calls: at most ⌈(lines+seeds)/64⌉ + k·log₂ n.
- **`evals/recall/`:** `--k` (or a `topk-k<N>` variant) sets k; `run.json` records it.
- **Test layout:** the real-host suites (`tests/host/integration.test.ts`, the paired evidence run and no-call plan in `tests/host/evidence-benchmark.test.ts`) run through `bun run test:host`, which CI also runs. `bun run test` covers the rest. The retrieval comparison builds its report and tree once per file.

## 0.7.0 — 2026-10-11

- **`chat_search(text, kind, limit, before)`:** finds stored messages containing every word of `text`, case-insensitively, newest first, with ~240-byte snippets and `before` paging. It reads the original log, so it reaches names, paths, numbers and errors that summaries dropped. Memory tool calls and search/recall results are never hits. Child views search only their snapshot. Always on with memory, like `zoom`.
- **`zoom(id, n, depth)`:** opens up to 4 levels at once (`2^depth` lines). `depth` 1 is the old behavior, byte for byte.
- **Recall gate (on by default; `--no-optchat-recall`):** registers `chat_recall(question)`. The judge scores the view lines, the best line at or above `--optchat-recall-min` (default 0.5) is opened, and one two-way choice per level leads to a single message, returned with its descent path and first 8 KB. At most ⌈lines/64⌉ + log₂ n judge calls, 20 s overall and 5 s per call. Failures return an explicit "recall failed" result.
- Tool names carry a `chat_` prefix because OMP reserves `search` (alias of `grep`) and `recall` (builtin).
- The tool gate never screens `chat_search` or `chat_recall`. `/optchat status` shows the recall gate. The memory guide in the system prompt documents both tools, so its bytes change once (the evidence runner's pinned system-block size is 6277 bytes).
- Memory-only harnesses (integration tests, smoke, `evidence:recall`) also opt out of the recall gate.
- **`bun run evidence:retrieval`:** offline, deterministic comparison of zoom, zoom depth, `chat_search`, prefetch, `chat_recall` and a scripted beam descent over a synthetic tree with planted facts (fake summariser and judge, no provider calls). Two seeds: summary navigators found only the facts whose topic survived in the view (3/12, 5/12); `chat_search` found 12/12; `chat_recall` needed one agent step where zoom needed about 200. Mechanics only, not a quality claim; details in ticket 10.

- Scheduling ([#3](https://github.com/ericjuta/omp-optchat/issues/3)): dependency-ready queues replace tree scans. Leaves are admitted while fewer than eight earlier leaves are unbuilt, and parents become ready as soon as both children exist. Failed calls release their slot at once and retry on the next appended message. `--optchat-retry-ms` is removed.
- The compactor tiling and its batch latch persist in `view.json` v2 together with the main view, in one atomic snapshot. Restarts reproduce the exact compactor prefix. v0.3.0 snapshots migrate once without changing the main tiling.

If no shortening attempt fits a 16 KB safety ceiling, the leaf fails instead of being cut. Images in user, assistant, tool, and report messages are stored content-addressed and returned by `zoom` after restart. Records keep the host event timestamp.
- Subagents ([#5](https://github.com/ericjuta/omp-optchat/issues/5)): task, async, and launch reports are stored as `work` records with provenance (job ID, agent ID, name, source, completeness). They are captured before the ordinary tool cap, with full structured data and typed artifact hydration. A report is labeled incomplete when the host delivered only a preview. The new `work(name, offset)` tool retrieves them. Opt-in `--optchat-child-view` gives subagents a frozen, read-only snapshot with `zoom`/`date`/`work`. Every read and prompt injection checks both the parent's live publication and the child's adopting session. The snapshot is revoked on switch or shutdown and never opens a second writer.
- Host frontier ([#7](https://github.com/ericjuta/omp-optchat/issues/7)): `/optchat status` reports stateless-OpenAI, settlement-deadline, host-maintenance, request-correlation, and child-view caveats. Host APIs that OMP 18.9.0 does not expose are tracked upstream and are not worked around.
- Evidence ([#6](https://github.com/ericjuta/omp-optchat/issues/6)): `bun run evidence:recall` is an opt-in, budgeted, synthetic-only recall and usage runner against real models. It runs in an isolated HOME and agent directory, copies only the selected credentials, and checks the effective system prompt for private context before any call. `OPTCHAT_METRICS_FILE` records compressor usage as content-free JSON lines. Measured on OMP 18.9.0 with Sonnet 4.6 and Haiku 4.5: 15 of 16 recall questions correct, all 16 grounded in zoomed originals, none hallucinated, including after a process restart. See README for usage figures, which are a sample and not a savings claim.
- Task reports that OMP delivers as nested previews are recorded as incomplete. Agent IDs never authorize file reads.
- Import/export accept `work` records with metadata. `exportJsonl` provides a lossless export.
